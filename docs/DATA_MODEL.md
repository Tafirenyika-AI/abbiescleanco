# Data Model

Source of truth: `prisma/schema.prisma` (30 models). This document explains *why* each group exists and calls out the gaps against the blueprint's suggested table list (§5) — it does not repeat the field-by-field schema, which is easier to read directly from the file.

## 1. Current models, by purpose

| Group | Models | Notes |
|---|---|---|
| Identity | `AdminUser`, `User`, `Customer` | Two disjoint auth roots (see `docs/SECURITY.md` §1). `Customer.userId` links a customer profile to a login; a `Customer` can exist without a `User` (guest checkout) and gets one later via account claim/signup. |
| Property | `Address` | Belongs to a `Customer`; a `Lead`/`Booking` points at one. No property-level preference/history object yet (blueprint's `properties`/`property_preferences`) — `Customer.notes`/`petsNote`/`accessInstructions` are the closest equivalent, and they're customer-level, not property-level. |
| CRM | `Lead`, `QuoteRequest` | `Lead` carries status/source/campaign/lostReason; `QuoteRequest` is the 1:1 "what they actually asked for" detail (property size, condition, add-ons, computed estimate range). Split this way so `Lead` stays a stable pipeline record even as estimate logic changes. |
| Quoting | `Quote`, `QuoteItem`, `PromoCode` | `Quote.status` (`DRAFT/SENT/ACCEPTED/DECLINED/EXPIRED`) — draft quotes are explicitly filtered out of every customer-facing query (verified this session: a `DRAFT` quote returns 404 to the customer, not just "hidden in the UI"). |
| Catalog | `ServiceCatalogItem` | Real content-managed table (`/admin/content`). `ServiceAddon` and `PricingRule` models exist in the schema but are **not used by any code path** — actual pricing config lives in `BusinessSetting` (JSON blob, see `pricingStore.ts`). These two models are dead schema, not dead features; leave them or drop them in a future cleanup, don't build on them without checking first. |
| Scheduling | `Booking`, `BookingStatusHistory`, `RecurringSchedule` | `RecurringSchedule` is schema-only — no store function or route reads/writes it. Recurring service is a real gap if the business wants to sell recurring cleaning (pricing engine has a `recurringDiscountRates` concept already, currently **disabled by design** pending client-approved rates — see `pricing.ts`). |
| Payments | `Payment` | `method` field added 2026-09-18 to support the 6 non-Stripe payment methods the business actually uses. `stripePaymentIntentId` links webhook events back to a payment row idempotently. |
| Communication | `CommunicationPreference`, `Message`, `MessageTemplate` | `Message`/`MessageTemplate` are schema-only (no inbound/outbound messaging code exists — the blueprint's "two-way inbound messages where provider permits" is not built). `CommunicationPreference` is real and enforced (see `docs/REPO_AUDIT.md` §3). |
| Automation | `AutomationEvent` | One row per scheduled send (type/status/scheduledFor/processedAt), processed by `/api/automation/process`. This is the closest thing to the blueprint's `workflow_runs` — it tracks send-level state, not a generic workflow engine. |
| Content | `Review`, `Faq`, `GalleryItem`, `ServiceArea`, `BusinessSetting` | `BusinessSetting` is a deliberate catch-all (`key`/`value` JSON) used for pricing config, automation rules, integration credentials, and branding — a pragmatic choice over adding a column per setting, at the cost of no schema-level validation on its contents (each reader validates its own shape). |
| Ops | `AuditLog`, `AdminNotification`, `ContactMessage`, `Notification` | `Notification` (singular, older) appears superseded by `AdminNotification` (plural, newer, actually used everywhere) — worth confirming `Notification` is truly dead before the next cleanup pass. |
| Workforce | `TeamMember`, `Expense`, `ExpenseCategory` | Flat, admin-only. No login, no self-service, no documents — see gap list below. |
| Client detail | `Attachment`, `ClientNote`, `PhotoEstimate` | Added 2026-09-19. All three are scoped by `(customerId, leadId?, bookingId?)` and every read is filtered by the authenticated `customerId` — this is the enforcement point tested in this session's IDOR pass. |

## 2. Gaps vs. the blueprint's suggested table list (§5)

Tables the blueprint suggests that **do not exist**, grouped by why they'd be needed:

- **Multi-tenancy**: `organizations`, `locations`, `service_zones`. Not needed unless the business actually expands to multiple locations/tenants — building this speculatively would add a foreign key and a filter to nearly every query for no current benefit. Flagged as a decision for the owner, not a default build.
- **Marketing/CRM depth**: `lead_sources` (currently a free-text `Lead.source` string, not a managed table — fine at current scale, would need normalizing if channel-level reporting gets serious), `campaigns`, `creatives`, `campaign_approvals`, `attribution_events`. None exist; no code reads/writes UTM parameters beyond `campaign` (a single optional string).
- **Availability/capacity as data**: `availability` — today "availability" is *computed* (`bookingAvailability.ts` walks business hours minus existing bookings) rather than stored. This is simpler and always-consistent; only worth becoming a real table if per-cleaner capacity (not just business-wide hours) needs modeling, which requires the workforce module that doesn't exist yet.
- **Jobs vs. Bookings**: the blueprint separates `bookings` (customer-facing commitment) from `jobs`/`job_assignments`/`job_checklists` (crew-facing execution). Today `Booking.staffAssignee` is a single free-text field — there's no real assignment, no checklist, no per-job media distinct from `Attachment` (which is already customer-facing/crew-visible, not a separate "after-service QA" concept).
- **Finance**: `invoices`, `invoice_lines`, `journal_entries`, `partner_payables`, `bills`. None exist — `Quote` + `Payment` are doing informal invoice duty.
- **Media consent**: `media_consents` as its own table. Today, consent is implicit in the act of uploading through the customer portal (which is behind auth and the customer's own action) — there's no separate recorded consent artifact, no expiration, no per-file deletion-request tracking beyond the existing soft-delete (`Attachment.deletedAt`).
- **Platform ops**: `webhook_events` (dedup/audit table — today the Stripe webhook trusts signature verification + `stripePaymentIntentId` uniqueness for idempotency, but there's no standalone log of raw webhook deliveries for replay/debugging), `workflow_runs` (partially covered by `AutomationEvent`, not generic), `ai_requests`/`ai_usage` (no AI cost/usage tracking exists at all — a real gap given the photo-estimate feature calls a paid model), `approvals` (no generic approval-gate table — the closest analog is `Quote.status` and `Review` moderation, both bespoke), `feature_flags` (none exist — every feature is either shipped or not; the "recurring discount disabled" toggle is a one-off boolean in `BusinessSetting`, not a flag system).

## 3. Indexing and tenant/record-scoping

Every table that a customer can reach has an indexed foreign key back to `Customer`/`Lead`/`Booking` used as the authorization filter (`@@index([customerId])`, etc. — see `Attachment`, `ClientNote`). `Booking` and `Lead` are indexed on `status` and `createdAt`/`scheduledStart` for the admin list views. No query in the current codebase does a full-table scan on a customer-facing path (spot-checked `clientPortalStore.ts`, `customerHistory.ts`). This has not been load-tested (no production traffic yet), so this is a design observation, not a measured guarantee.
